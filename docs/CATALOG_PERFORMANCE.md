# Catalog rendering performance — first stage

Audit of public catalog: the old page mounted every matching product card (several thousand possible), including quantity controls, hooks and image elements. Search ran over the full array and reconciled that entire grid on each keystroke. The privileged missing-photo export also automatically probed every candidate image, up to 8 concurrent requests, on catalog entry.

Changes: paginate the already-loaded full result into a maximum of 48 cards per page, search/filter the full array before slicing, preserve the result count, allow all pages, reset/clamp page by filter scope, memoize ProductCard and stable add handler. Single-pass filtering keeps previous exact matching/stock semantics. Missing-photo audit starts only on explicit request, caps concurrency at 4, deduplicates URLs, cancels active probes and does not expose partial results. Includes verified local photos in the audit. Parse static manifest only once per module. No changes to API, stock/price/order logic, price lists, images, session/cart persistence or public source flags.

The initial API request still returns the full product list. Actual browser latency is not measured in this change. If initial loading remains slow, inspect Network timings for GET /api/catalog (and catalog admin endpoints); legacy catalog SQL uses a correlated LATERAL with OR and trimmed barcode. Obtain EXPLAIN and actual timings before modifying SQL or cache/freshness semantics. No migrations, no auto deploy. QA covers a synthetic 7,602-product catalog, exact barcode search across pages, stock/category combinations, duplicate keys, existing price-list/order/photo contracts, builds with flag OFF/ON.
